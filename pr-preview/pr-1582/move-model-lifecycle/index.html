Move Model Lifecycle

This document illustrates the lifecycle of key Move models in the deposit and withdrawal flows, showing how data structures transform between onchain (Sui) and offchain (Bitcoin) states.

What is the entry-function gating principle?​

Every entry function that takes the Hashi object asserts the package version is enabled. Beyond that, pause and reconfiguration gate only the deposit and withdrawal flows. The table shows which entry functions stop when governance pauses the system and which stop while a committee handoff is pending.

Entry functionsStops during a pauseStops while a committee handoff is pending
Deposit approval (approve_deposit()) and confirmation (confirm_deposit())YesYes
Withdrawal approval (approve_request()), commitment, signing, and finalization (finalize_withdrawal())YesYes
User requests (deposit(), request_withdrawal())YesNo
Withdrawal confirmation (confirm_withdrawal())YesNo
Withdrawal cancellationNoNo
Reconfiguration, MPC certificate submission, governanceNoNo
Cleanup entries: cleanup_spent_utxos, archive_confirmed_withdrawals, archive_withdrawal_requests, finish_archive_withdrawal_txns, destroy_key_gen_certs, destroy_nonce_certs, delete_expired_deposit, proposal::delete_expiredNoNo
Validator registration or key rotationNoNo

The last 4 rows never check pause, because an emergency pause must not block operators from maintaining nodes or the chain from shedding dead state. Nodes themselves stop all leader work while paused, garbage collection included, so during a pause only a manual call sheds that state. One asymmetry is intentional: users can request deposits and withdrawals during reconfiguration (a withdrawal request only escrows their hBTC); only committee approval, commitment, signing, and deposit confirmation wait for the new committee.

How do Move models change during a deposit?​

During a reconfiguration, users can still call deposit(), but approval and confirmation wait for the new committee; see What is the entry-function gating principle?.

How do Move models change during a withdrawal?​

During a reconfiguration, users can still call request_withdrawal() and withdrawal confirmation still proceeds, but approval, commitment, signing, and finalization wait for the new committee; see What is the entry-function gating principle?.

info

The config key bitcoin_confirmation_threshold (default 6) stores the Bitcoin confirmation threshold onchain. Hashi stores witness signatures onchain so that any leader can reconstruct and re-broadcast the signed Bitcoin transaction without MPC re-signing (for example, after leader rotation, mempool eviction, or a Bitcoin reorganization).

Limiter coordination. The LocalLimiter on each committee node is a deterministic projection of the onchain stream. Outside a reconcile (below), its next_seq advances only when the node's object mirror sees a WithdrawalTransaction become fully signed (the finalize_withdrawal write). The finalize path uses validate_consume (read-only) to gate participation, never to mutate state: the leader checks before it calls the guardian, and each member checks again before it signs the finalize certificate. The leader's flow only reaches finalize_withdrawal() after finalize_withdrawal_through_guardian returns Ok, so seeing the transaction become fully signed onchain is a sufficient proxy for the guardian having acknowledged the request. The guardian advances its own next_seq when it signs, so the local cache trails it while a withdrawal is in flight. On startup, each node seeds its LocalLimiter through GetGuardianInfo, then periodically reconciles against it, snapping back a cache that stalled or drifted and adopting a new limiter policy after a guardian rotation.
