Module audit

Expand description

The batch and continuous auditors. The auditor core, shared by the batch and continuous auditors.

Why it exists: both auditors read the same sources and judge the same flows. They differ only in when they poll and when they stop. The core holds one state machine per pending withdrawal and per pending deposit, and the auditors drive it.

How it works:

  1. The Sui and guardian pollers return events, and the core ingests each one into its withdrawal’s or deposit’s state machine. A contradictory event is reported and dropped.
  2. Each tick, the core looks up on Bitcoin every machine that expects a Bitcoin event, and ingests the confirmations it finds.
  3. A Sui approval still missing after its deadline is fetched by its withdrawal id, since the Sui scan may have started after it.
  4. Each tick, the core reports the violations of every machine in the audit window: the expected events whose deadline a cursor has passed.
  5. Completed machines are garbage collected.
  6. The progress watermarks give the time through which every flow is verified, which is where a restart starts.

Assumptions:

  • The user’s window is on the guardian timeline. A withdrawal is in the window if any of its events is, so an orphan E1 in the window is reported too.
  • Deposits are checked over the Sui range the window derives, not gated by the window.
