Module audit

Expand description

The auditor core and the continuous auditor. The auditor monitors bridge events and reports findings.

Why it exists:

  • The monitor checks deposits, withdrawals, and unspent transaction outputs (UTXOs).
  • Metrics provide findings and source progress for alerts.

How it works:

  1. Restore the source positions, flow machines, and UTXO pool from a snapshot.
  2. Without a snapshot, start at the bridge genesis with an empty pool. Fail at startup on the snapshot of another deployment.
  3. Fail at startup if the Sui node has pruned the start checkpoint.
  4. Read Sui events and guardian logs into the flow machines. At startup, catch up Sui, then the guardian, then Bitcoin. Retry a failed source until it is current. Then remove the closed machines and save the snapshot. Only then start the loop, so the loop does not start with a large unanswered backlog.
  5. Check Bitcoin confirmations after both withdrawal approvals arrive. Check that each fresh deposit approval names an unspent outpoint.
  6. Every MAINTENANCE_INTERVAL, run one maintenance tick in this order:
    1. Remove the closed machines and add their flows to the pool. Log the open flows. This step is first, so each later step sees only open machines and a current pool.
    2. Check Bitcoin when the daily pool check is due.
    3. Check that the UTXO pool backs the hBTC supply.
    4. Report timing violations and judge suspect spends. These two have no order rule.
    5. Report a source, the daily pool check, or the hBTC supply read that is behind its limit. This step comes after steps 2 and 3, so a check that succeeds in this tick is not stale.
    6. Save the snapshot once SNAPSHOT_SAVE_INTERVAL seconds have passed since the last save. Then report a save that is behind its limit. This step is last.
  7. Check Bitcoin at the first maintenance tick. Repeat successful pool checks after UTXO_CHECK_INTERVAL seconds.
  8. Judge suspect spends after the Sui cursor passes the Bitcoin lookup time.
  9. In the loop, log a failed source tick. The next tick of that source retries it.

Assumptions:

  • Every tick runs on one task. The first catch-up blocks the maintenance tick, so a first run reports no stale source while it catches up.
  • A source that stays down at startup blocks the loop. The Sui checked_through gauge then stops too, and its lag alert pages. Only the Sui gauge has a lag alert.
