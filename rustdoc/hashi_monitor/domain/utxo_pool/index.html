Module utxo_pool 

Source
Expand description

The monitor’s own record of the UTXOs the bridge holds, built from Bitcoin facts.

Why it exists: the committee writes Move’s utxo_records. A compromised committee can mark a UTXO spent on Move without spending it, or keep a deposit out of Move, then spend the UTXO alone when the 60-day recovery leaf opens. Only a Bitcoin fact changes this pool, so the committee cannot remove a UTXO from it or keep one out.

How it works:

  1. The pool starts empty at the bridge’s genesis. The snapshot keeps it across restarts.
  2. A deposit enters when Bitcoin confirms the request’s output at the bridge script of the claimed path.
  3. A complete withdrawal (E1, E2, E3) removes its inputs and adds its change. The guardian’s E2 labels the change; the monitor verifies it.
  4. In one pass, every add comes before every spend.
  5. A second add of a held UTXO is a repeat. A second amount or script is an BtcRpcInconsistency. A spend of a UTXO the pool does not hold is UtxoUnknownInputSpent.
  6. A DepositApproved must match a held deposit’s amount and script.
  7. Once a day, check asks Bitcoin about every held UTXO. It reports old, spent and missing UTXOs.
  8. The pool keeps no record of spent UTXOs. Move refuses a request after the first DC, so every add for a UTXO comes before its spend.

The pool can hold a UTXO that Move never holds, for example a deposit that AML screening rejects or a request with a wrong amount.

Assumptions:

  • The first run starts at genesis, so the monitor sees every UTXO enter.
  • Sui and the guardian deliver each event once: no repeat and no miss.
