hashi_monitor::rpc

The Bitcoin client: confirmation lookups over HTTP JSON-RPC.

Why it exists: the withdrawal E3 and the deposit E1 are Bitcoin confirmations. Bitcoin has no event stream to scan, so the auditor looks each pending transaction up by txid.

Why one height:

  • A parent transaction creates an output that a dependent transaction spends.
  • At one height, the dependent cannot have more confirmations than its parent.
  • All lookups in a tick use one captured height, including lookups in different batches.
  • New blocks between RPC responses must not complete a dependent machine before its parent is ready to close.
  • Pool maintenance needs each complete flow’s parent machine already closed or ready to close.

How it works:

  1. At startup, the auditor reads Hashi’s on-chain bitcoin_confirmation_threshold and gives it to the client. A transaction counts as confirmed at that depth, as it does for the committee. On mainnet, a threshold below MAINNET_MIN_CONFIRMATIONS stops the monitor.
  2. Before a pass, synced_height checks the node and returns its height. The node must follow deployment.bitcoin_network, be out of initial block download, and have a tip no older than max_tip_age, which the auditor sets to its SOURCE_STALE_LIMIT. At the first check, a node that reports its indexes must have a synced txindex. A failed check fails the pass, so a wrong node, or one with an older tip, becomes a SourceStale finding. Until its tip passes that age, a frozen node still gives lookup findings. All batches use this height to calculate confirmation depth. Blocks that arrive during the pass count on the next pass.
  3. prefetch_confirmations looks all pending txids up in batches of HTTP_JSON_RPC_BATCH_SIZE, with HTTP_JSON_RPC_BATCHES_IN_FLIGHT batches sent at once, and lookup_confirmation serves each one from that cache. A confirmed answer is kept across passes: a confirmation at the threshold depth does not change. forget_unconfirmed drops the rest at the start of each pass, so an unconfirmed transaction is looked up again. An answer for a txid no longer asked for is dropped. When a lookup fails, the batches that finished are kept, so the next pass asks only about the rest.
  4. A transaction at the threshold depth is returned with the time of its own block and the time of the block that gave it that depth.
  5. Requests are not paced: the node is the bridge’s own. A request that fails to send, gets an HTTP 502, 503 or 504, or is rate limited is retried with exponential backoff, MAX_REQUEST_RETRIES times. Core answers a JSON-RPC error with HTTP 500, so 500 is not retried.

Assumptions:

  • The threshold is read once. A governance change takes effect in the monitor at its next restart.
  • An unconfirmed answer is never reused across passes. So the auditor can stamp every answer with the pass’s start time: the real lookup is no earlier. A cached confirmed answer does not need a time.
  • The endpoint serves getrawtransaction with verbose output, which needs txindex or a hosted provider. A hosted provider that does not serve getindexinfo is not checked for an index.
  • A request that still fails after the retries fails the pass, which is retried on the next tick.
