The Bitcoin client: confirmation lookups over HTTP JSON-RPC.

Why it exists: the withdrawal E3 and the deposit E1 are Bitcoin confirmations. Bitcoin has no event stream to scan, so the auditor looks each pending transaction up by txid.

How it works:

  1. Before a pass, ensure_synced fails while bitcoind lags its peers, since a lagging node reports recent transactions as unconfirmed.
  2. prefetch_confirmations looks all pending txids up in batches of HTTP_JSON_RPC_BATCH_SIZE, and lookup_confirmation serves each one from that cache. The cache is cleared at the start of each pass, so an unconfirmed transaction is looked up again next pass.
  3. A transaction with at least MIN_CONFIRMATIONS confirmations is returned with the time of its own block and the time of the block that gave it MIN_CONFIRMATIONS.
  4. Requests are paced by HTTP_JSON_RPC_BATCH_DELAY, and a rate-limited request is retried with exponential backoff.

Assumptions:

  • The endpoint serves getrawtransaction with verbose output, which needs txindex or a hosted provider.
  • Only rate limits are retried. Other transient failures fail the pass and are retried on the next tick.
