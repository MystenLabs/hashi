The Sui poller: the Hashi events read from Sui, in checkpoint order, and the hBTC supply.

Why it exists: the withdrawal E1 and the deposit E2 are Sui events. The poller scans the checkpoints for them and gives each one its time. It also reads the hBTC supply; see hbtc_supply.

How it works:

  1. The poller starts at a checkpoint: on a first run, the one that holds the Hashi package’s publish transaction; on a resume, the one the snapshot saved. Before the first poll, it checks that the node still serves the start. It sets the progress timestamp from the checkpoint before the start.
  2. Each poll lists the transactions that emit a monitored event, from the next checkpoint through the checkpoint the caller names, but at most MAX_CHECKPOINTS_PER_POLL checkpoints. The caller names the chain head it read at the tick’s start. A failed range is retried, then split.
  3. The cursor advances through the last checkpoint the node declared complete. The transactions of later checkpoints wait for the next poll, so a checkpoint is ingested whole.

Assumptions:

  • Every monitored event type keeps the original package’s address across upgrades.
